## AI 产品实习版本

**基于 Text-to-SQL 的 AI 零售数据问答助手**  
技术栈：Python、Streamlit、SQLite、Pandas、Plotly、OpenAI-compatible API

- 面向产品/运营人员的自然语言问数场景，基于 12 万行公开零售销售数据设计 AI 数据问答原型，支持品类销售、渠道对比、时间趋势、用户分层等业务问题查询。
- 梳理业务问题、数据字段和指标口径，输出 PRD、数据字典、Prompt 设计记录、安全清单和评测报告，形成从需求、数据、Prompt 到评测复盘的产品闭环。
- 设计 Text-to-SQL Prompt，将表结构、字段约束和 GMV、订单数、客单价等指标口径注入提示词，降低字段幻觉和指标理解错误。
- 实现 SQL 只读安全校验和危险意图拦截，限制系统仅执行 `SELECT` 或只读 `WITH ... SELECT` 查询，拦截删除、修改、建表等高风险请求。
- 构建 20 条评测问题并自动生成评测报告，覆盖品类、渠道、时间趋势和安全测试，当前 SQL 执行成功率 90.00%，沉淀 2 条 Bad Case 用于 Prompt 和安全规则迭代。

## 数据产品 / 数据分析实习版本

**基于 Text-to-SQL 的 AI 零售数据问答助手**  
技术栈：Python、SQLite、Pandas、Streamlit、Plotly、OpenAI-compatible API

- 使用 12 万行零售销售数据构建本地 SQLite 分析库，将原始宽表拆分为 `fact_sales` 销售事实表和 `dim_product` 商品维度表，覆盖品类、品牌、渠道、地区、用户分层、销售额和折扣等字段。
- 基于 Streamlit 搭建数据问答 Demo，支持自然语言输入业务问题，自动生成 SQL 并返回查询表格、可视化图表和中文业务解释。
- 梳理 GMV、订单数、客单价、销售件数、平均折扣等指标口径，并在 Prompt 中加入表结构和字段约束，提升 SQL 生成稳定性。
- 设计 SQL 安全校验逻辑，限制系统仅执行只读查询，拦截多语句注入和 `DROP / DELETE / UPDATE / INSERT` 等危险操作。
- 维护 20 条评测问题，自动记录 SQL、执行状态、错误类型和 Bad Case，生成评测报告，当前 SQL 执行成功率 90.00%。

## 面试时 2 分钟介绍

我做的是一个基于 Text-to-SQL 的 AI 零售数据问答助手。项目背景是产品或运营同学经常需要查询销售数据，比如品类销售额、渠道表现、地区差异和用户分层贡献，但他们不一定会写 SQL。  

我使用 12 万行公开零售销售数据，先做数据理解和建模，把原始数据整理为销售事实表 `fact_sales` 和商品维度表 `dim_product`。然后用 Streamlit 做了一个本地 Demo，用户输入自然语言问题后，大模型会根据表结构、字段说明和指标口径生成 SQLite SQL，系统再做只读安全校验，最后展示查询结果、图表和业务解释。  

这个项目不只停留在能问答。我还整理了 PRD、数据字典、Prompt 设计记录、安全清单和评测报告，维护了 20 条评测问题，统计 SQL 执行成功率和 Bad Case。过程中发现过安全规则误杀只读 `WITH` 查询的问题，所以我把安全校验优化为允许只读 `WITH ... SELECT`，同时继续拦截删除、修改、建表等危险意图。

## 面试官追问准备

### 1. 这个项目为什么适合 AI 产品实习？

因为它不只是调用模型，而是覆盖 AI 产品落地里的几个关键环节：场景定义、数据理解、Prompt 约束、安全控制、效果评测和 Bad Case 复盘。

### 2. 你怎么保证模型生成 SQL 不乱来？

我做了两层控制。第一层是在 Prompt 中明确表结构、字段名、指标口径和只能生成查询语句。第二层是在代码里做安全校验，只允许 `SELECT` 或只读 `WITH ... SELECT`，并拦截危险关键词和多语句注入。

### 3. 评测怎么做？

我维护了固定的 `questions.csv`，覆盖品类销售、渠道对比、用户分层、时间趋势和安全测试。评测脚本会自动记录生成 SQL、执行状态、错误类型和 Bad Case，并生成 `evaluation-report.md`。

### 4. 项目的不足是什么？

目前还是本地 Demo，没有连接真实企业数据库，也没有权限系统和生产级日志。评测集目前是 20 条，后续可以扩展到 40 条以上，并进一步人工复核答案正确率。
