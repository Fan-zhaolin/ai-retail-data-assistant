AI 零售经营分析与运营 Agent

## 推荐技术栈

Python / Streamlit / SQLite / Pandas / Plotly / OpenAI-compatible API / Text-to-SQL

## AI 产品 / AI 应用实习版本

**AI 零售经营分析与运营 Agent｜个人项目｜2026.06 - 至今**
技术栈：Python、Streamlit、SQLite、Pandas、Plotly、OpenAI-compatible API

- 基于 12 万行公开零售销售数据设计经营分析原型，支持经营简报、自然语言查数、结果可视化、推荐追问和 SQL 依据复核；根据 3 名体验用户的两轮反馈调整问题前提校验、图表和结果表达。
- 将表结构、指标口径、业务词和能力边界拆为可配置语义层；对模型生成 SQL 进行只读校验，并在数据库层使用只读连接和查询中断限制。
- 增加订单、库存、退货政策查询与退货申请工作流；读操作自动执行，写操作必须人工批准，并通过独立操作库、幂等键和审计日志降低误执行与重复提交风险。
- 维护 15 条 Text-to-SQL 黄金问题和 30 条 Agent 固定任务；当前固定任务的路由与最终状态均为 30/30，项目共有 35 项单元测试通过。上述数字仅用于固定回归测试。

- 使用固定问题集区分 SQL 执行成功和业务答案正确，记录错误类型与 Bad Case；项目共有 35 项单元测试通过。

## 简历空间较小时的一行版本

基于 12 万行公开零售数据搭建经营分析与受控运营 Agent 原型，支持 Text-to-SQL、订单/库存/政策工具调用和需人工批准的退货申请；使用只读连接、幂等键、审计日志及 30 条固定任务评测控制风险。

## 面试时 2 分钟介绍

我最初做的是一个面向运营人员的 Text-to-SQL 零售分析助手。使用 12 万行公开销售数据，用户可以直接问品类、渠道和趋势问题，系统生成 SQLite SQL，通过只读安全校验后展示结论、图表和计算依据。

第一版能查数，但 3 名体验用户反馈主动提问的价值不明显、图表容易误导、固定数据源也很难说明扩展性。我据此增加经营简报、推荐追问、字段适配和确定性结论，并专门处理“为什么线上最差”这类前提可能错误的问题。

V2.2 没有为了简历直接套一个新框架，而是增加了可验证的运营任务：订单查询、库存查询、退货政策检索和退货申请。退货任务会先查订单，再读取政策和判断时间窗口；如果满足条件，只生成待执行动作，必须人工确认后才写入独立演示库。我还加入幂等键和审计日志，避免重复申请并保留执行轨迹。

目前项目有 15 条 Text-to-SQL 黄金问题、30 条 Agent 固定任务和 35 项单元测试。固定 Agent 任务当前全部通过，但我会明确说明这不等于真实开放式客服场景准确率。

## 面试官追问准备

### 1. 为什么没有使用 LangGraph？

当前只有订单、库存和政策三个读工具，加一个需要审批的写工具，流程边界明确。确定性路由更容易测试和控制；如果后续真实表达出现大量规则无法覆盖的 Bad Case，或者任务需要动态规划步骤，再引入模型路由或图编排。

### 2. 为什么可以叫 Agent，而不只是聊天机器人？

系统会根据任务选择工具，并在退货场景中连续完成订单查询、政策检索、资格判断和动作提议。不过当前是受控 Agent 工作流，不是能自主完成任意客服任务的通用 Agent。

### 3. 怎样避免 Agent 误操作？

分析库始终只读；写操作只能进入独立演示库；创建申请需要明确人工批准；订单号和原因生成幂等键；每一步记录路由、工具、状态和说明。满足退货窗口只表示可以提交申请，不自动退款。

### 4. Agent 评测怎么做？

维护 30 条固定任务，分别检查预期路由和最终状态，覆盖正常查询、不存在对象、缺少参数、退货超期、订单未送达和人工审批暂停。固定任务通过只说明回归稳定，后续还需收集真实开放式表达补充 Bad Case。

### 5. 数据真实吗？

销售数据来自公开数据集；物流状态、库存和退货政策是根据销售数据确定性生成的演示数据，页面和文档都明确标注，不能当作真实企业运营数据或业务收益。
