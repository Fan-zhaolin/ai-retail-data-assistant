# AI 经营分析助手 V2.1：真实用户反馈改版与学习手册

更新日期：2026-07-13

当前进度：V2.1 已在本地完成，24 项单元测试通过。渠道问题诊断、多系列中文图表、确定性结果结论、常见中英文字段适配和会话级 CSV 数据源均已完成浏览器验证。第二轮已收到 3 名用户的负面反馈，但修复后的 V2.1 尚未交给原用户复测，也尚未部署到公开 Demo。

这份手册用于指导你把当前的“AI 零售数据问答助手”改成更有产品价值、也更适合 AI 产品实习面试的 V2 版本。

目标不是继续堆功能，而是完成一次真实的产品迭代：

```text
第一版假设
-> 3 名用户实际体验
-> 发现价值、体验和扩展性问题
-> 重新确定目标用户与优先级
-> 完成最小改版
-> 让原来的用户复测
-> 用结果更新项目文档和简历
```

完成这轮之后，你要达到四个标准：

1. 能解释三条用户反馈分别否定了什么产品假设。
2. 能说清楚为什么选择这些改动，而不是盲目增加功能。
3. 能读懂并修改 V2 涉及的核心代码。
4. 能用第一次测试和第二次测试的差异证明产品发生了改进。

## V2.1 为什么继续改

第二轮反馈不是简单的“用户不喜欢”，而是暴露出三个可以验证的设计错误：

1. 用户问“为什么线上最差”时，系统接受了一个错误前提，也没有区分网页端和“网页端加手机端”的线上口径。
2. 月份和渠道同时出现时，图表把不同渠道的数据点串成一条线，属于图表逻辑错误，不只是视觉审美问题。
3. 会话级上传只解决同公司固定模板更新，没有解决不同公司的常见字段命名差异。

V2.1 对应增加四个机制：

```text
为什么类问题 -> 先核对前提 -> 再拆订单数和客单价 -> 最后声明因果边界
时间加分类字段 -> 按分类拆成多条折线 -> 中文月份、图例和金额单位
外部销售明细 -> 常见中英文字段别名映射 -> 补全可选字段 -> 再做类型校验
查询结果 -> 程序计算排名、峰值和变化率 -> 不让模型自由复述数字
```

这里仍然有边界：字段适配只面向单张销售明细表，不等于能自动接入任意企业的多表数据库。

## 一、当前事实与表达边界

### 1. 已经发生的真实反馈

将三位体验者匿名记为 U1、U2、U3，不记录姓名和联系方式。

| 用户 | 原始反馈 | 暴露的问题 |
| --- | --- | --- |
| U1 | “感觉没什么用，图个新鲜，问手下不就好了。” | 对管理者来说，主动输入问题的查数工具不一定比现有协作方式更方便。 |
| U2 | “画面好丑，没有用下去的欲望，也没有帮我扩展，只有数据我自己打开表看不就好了，还能摸摸鱼。” | 页面缺乏吸引力；产品只返回数据，没有主动提供结论、分析方向和继续探索的理由。 |
| U3 | “还可以，但是公司新的数据怎么办，未来接入更庞大更复杂的数据怎么办，还能用吗？” | 当前固定数据集能演示功能，但没有证明数据更新、换表结构和扩大数据规模后的可用性。 |

### 2. 现在可以说什么

可以说：

> 邀请 3 名非 SQL 用户体验第一版，收到了关于使用价值、页面体验和数据扩展性的负面反馈，并据此重新调整 V2 优先级。

现在不能说：

> 通过用户调研证明产品有明确市场需求。

也不能说：

> 已经解决企业级数据接入和大规模数据分析问题。

原因是目前只有 3 名体验者，V2 虽已完成本地开发，但尚未经过第二轮复测。负面反馈是真实证据，但不是市场规模证明。

## 二、三条反馈应该怎样理解

### 反馈一：为什么不直接问手下

这不是用户“不懂产品”，而是第一版的目标用户定义不够准确。

管理者有下属、有固定报表和沟通习惯。让管理者重新学习一个工具、自己组织问题，未必比发一句消息更省事。

因此 V2 不再假设所有管理者都愿意主动查数，而是拆成两个使用场景：

| 场景 | 用户 | 产品应该提供什么 |
| --- | --- | --- |
| 经营简报 | 小团队负责人、业务负责人 | 打开页面就能看到变化、异常和重点提醒，不要求先提问。 |
| 自助分析 | 缺少数据支持的运营、产品和业务人员 | 用自然语言查询数据，并通过推荐问题继续分析。 |

你要记住：管理者更需要“主动送来的重点”，业务执行者更需要“随时可以自助查询”。

### 反馈二：为什么不直接打开 Excel

如果产品只把自然语言变成另一张表，它确实没有形成足够价值。

V2 的结果页不能继续以数据表为主，而应按下面顺序展示：

```text
一句话结论
-> 关键指标
-> 最合适的图表
-> 值得关注的变化或异常
-> 3 个可以继续追问的问题
-> 数据明细
-> SQL 与查询依据
```

其中，数据明细和 SQL 仍然保留，但放进“查看数据与计算依据”区域。这样既照顾普通业务用户，也保留可复核性。

注意：系统可以指出“哪个指标变化明显”，但当前不能擅自声称“这就是下降原因”。没有成本、活动、库存等字段时，只能称为相关线索，不能称为因果结论。

### 反馈三：新数据和复杂数据怎么办

对这个问题必须诚实：当前版本不能直接接入任意一家公司的复杂数据库。

当前 `src/prompts.py` 中写死了表结构、指标口径和枚举映射；`src/db.py` 默认读取固定 CSV 并生成固定 SQLite 数据库。换成完全不同的数据后，需要人工修改代码。

V2.1 不追求一次做成企业级 BI 平台，而是证明三个能力：

1. 常见中英文字段名的销售明细 CSV 可以自动映射、校验并继续查询。
2. 表、字段、指标、关联关系和业务词不再全部写死在 Prompt 代码中，而是由独立语义配置管理。
3. 无法自动适配的核心缺失字段和复杂多表场景会明确拒绝，而不是假装理解。

完成这两点，就能合理说明系统具备初步扩展思路。MySQL、PostgreSQL、数据仓库、权限和大规模并发仍作为后续方向，不冒充已完成功能。

## 三、V2 产品定义

### 1. 暂定名称

对外项目名暂时保留“AI 零售数据问答助手”。

完成经营简报、推荐追问和数据配置后，再统一改成：

> AI 零售经营分析助手

没有完成改版前不要提前改名，否则名称承诺会超过当前能力。

### 2. 主要用户

第一目标用户：没有专职数据分析支持，需要自己查询销售数据的运营、产品和业务人员。

第二目标用户：希望快速查看经营重点的小团队负责人。

暂时不作为目标用户：拥有成熟 BI 系统、专职数据团队、复杂权限和实时数仓的大型企业。

### 3. 核心价值

V2 的一句话定位：

> 将零售交易数据整理成可直接阅读的经营简报，并支持业务人员通过自然语言继续查询和追问。

它不再只解决“不会写 SQL”，还要解决三个问题：

1. 不知道应该先看什么。
2. 看到了数字但不知道哪里值得关注。
3. 得到答案后不知道下一步应该继续问什么。

### 4. 本轮明确不做

1. 不做登录和完整企业权限系统。
2. 不承诺接入任意数据库。
3. 不做实时流式数据。
4. 不做自动预测和因果分析。
5. 不做复杂拖拽式 BI 仪表盘。
6. 不用大量装饰掩盖数据和产品问题。

这些不是“以后永远不做”，而是本轮为了验证核心价值主动控制范围。

## 六、第 0 步：开始前检查

打开 PowerShell，输入：

```powershell
cd E:\实习项目\ai-data-assistant
git status --short
git branch --show-current
git diff -- docs/evaluation-report.md eval/results.csv eval/bad_cases.csv
```

你要理解：

1. `git status --short` 查看哪些文件被修改或新增。
2. `git branch --show-current` 查看当前分支。
3. `git diff` 只查看变化，不会删除任何内容。

当前工作区已有评测生成文件和学习文档变化。不要执行 `git reset --hard`，也不要直接删除这些文件。V2 开始前先确认哪些是需要保留的结果。

### 任务 3：避免伪洞察

允许说：

> 线上渠道净销售额比上月下降 12%，值得继续查看品类和地区分布。

不允许说：

> 线上销售下降是因为营销活动失败。

第二句话需要营销活动字段或其他证据，当前数据不支持。

### 第 3 天验收

1. 不输入问题也能看到经营简报。
2. 所有数字都能用 SQL 复核。
3. 查询后出现 3 个可点击追问。
4. 点击追问后，问题自动进入下一次分析。
5. 没有把相关变化写成因果结论。

## 十、第 4 天：拆出可配置语义层

### 为什么要做

当前表结构和业务规则主要写在 `src/prompts.py` 中。这样做适合第一版，但换数据时需要直接改 Python 代码。

V2 增加：

```text
config/semantic_model.json
src/semantic_model.py
```

### `semantic_model.json` 应该保存什么

参考结构：

```json
{
  "tables": {
    "fact_sales": {
      "description": "销售事实表",
      "columns": {
        "transaction_id": "交易编号",
        "transaction_date": "交易日期",
        "product_id": "商品编号",
        "sales_amount": "净销售额"
      }
    },
    "dim_product": {
      "description": "商品维度表",
      "columns": {
        "product_id": "商品编号",
        "category": "商品品类"
      }
    }
  },
  "joins": [
    "fact_sales.product_id = dim_product.product_id"
  ],
  "metrics": {
    "净销售额": "SUM(fact_sales.sales_amount)",
    "订单数": "COUNT(DISTINCT fact_sales.transaction_id)",
    "客单价": "SUM(fact_sales.sales_amount) / COUNT(DISTINCT fact_sales.transaction_id)"
  },
  "synonyms": {
    "美妆": "Beauty",
    "手机端": "Mobile App"
  },
  "unsupported_fields": [
    "库存",
    "成本",
    "利润",
    "退货"
  ]
}
```

实际配置必须补齐当前项目使用的全部字段和规则，上面只是结构示例。

### `semantic_model.py` 应该负责什么

1. 读取 JSON。
2. 检查必须字段是否存在。
3. 检查指标是否为空。
4. 检查关联关系引用的表和字段是否存在。
5. 将配置转换为 Prompt 使用的文本。

建议函数：

```python
def load_semantic_model(path="config/semantic_model.json") -> dict:
    ...

def validate_semantic_model(model: dict) -> None:
    ...

def build_semantic_context(model: dict) -> str:
    ...
```

随后让 `src/prompts.py` 调用 `build_semantic_context`，而不是继续维护一大段写死的 `SCHEMA`。

### 必须新增的测试

建议新增 `tests/test_semantic_model.py`，覆盖：

## 十一、第 5 天：安全的数据更新能力

### 本轮只支持什么

支持单张销售明细 CSV，并自动识别订单号、日期、品类、渠道、销售额、单价、数量等常见中英文字段名。不支持任意文件、多表自动合并或企业数仓自动理解。

上传前必须检查：

1. 字段别名映射后，订单号、日期、品类、渠道等核心列是否齐全。
2. 日期是否能解析。
3. 金额和数量是否为数字。
4. 是否有空商品编号。
5. 数据量是否超过演示限制。

### 为什么不能直接覆盖公共数据库

公共 Streamlit Demo 可能同时被多人访问。如果一个匿名用户上传文件后直接覆盖 `data/app.db`，其他用户会看到被修改的数据，还可能造成数据泄露和并发冲突。

因此 V2 采用“会话级临时数据源”：

```text
用户上传 CSV
-> 常见中英文字段映射和可选字段补全
-> 核心字段和类型校验
-> 为当前会话生成临时 SQLite 文件
-> 当前会话查询临时库
-> 会话结束后不再保留
-> 公共演示库始终保持只读
```

建议重构：

```python
def build_database_from_dataframe(df, db_path):
    ...

def run_sql(sql, db_path=None):
    ...
```

原来的 `run_sql(sql)` 仍默认查询公开演示库；只有当前会话明确选择上传数据时，才传入临时库路径。

### 页面需要显示

1. 当前数据源：演示数据或用户临时数据。
2. 数据行数。
3. 日期范围。
4. 上传和校验结果。
5. “临时数据仅用于当前会话，不会保存”的说明。

### 必须新增的测试

1. 缺少必需字段时拒绝导入。
2. 常见中文字段能映射到内部标准字段。
3. 日期格式错误时给出具体字段名。
4. 正确 CSV 能生成可查询的临时数据库。
5. 临时数据库不会覆盖正式 `data/app.db`。
6. 查询仍使用只读连接和执行限制。

### 第 5 天验收

1. 上传常见中文字段名的新数据后，页面展示映射关系，概览和查询结果随之变化。
2. 上传错误文件时，页面指出具体缺失或错误字段。
3. 刷新或新开会话后，公共演示数据仍然正常。
4. 你能解释为什么不能允许匿名用户覆盖公共数据库。
