# 零售运营 Agent V2.2 设计说明

更新日期：2026-07-20

## 1. 为什么升级

V2.1 已能完成经营简报、自然语言查数和结果解释，但主要解决“看数据”的问题，不能证明系统如何处理需要多个步骤、调用不同工具且包含风险动作的业务任务。

V2.2 选择订单查询、库存查询和退货申请作为扩展场景，原因不是电商概念热门，而是这个场景能同时验证：

1. 用户表达如何被路由到不同工具。
2. 一个任务如何组合多个步骤。
3. 读操作和写操作如何使用不同权限。
4. 写操作出错或重复提交时如何控制风险。
5. 每一步能否被记录、复核和评测。

## 2. 数据事实与演示边界

原公开数据只包含销售交易，不包含真实物流、库存、退货和退款记录。因此 V2.2 不虚构真实业务数据，而是从公开销售数据确定性生成三个演示表：

- `ops_orders`：保留订单、商品和金额，按演示日期生成处理、发货和送达状态。
- `inventory_snapshot`：按商品编号生成可复现的库存、预留量和补货点。
- `return_policies`：为公开数据中的品类配置演示退货窗口和复核说明。

页面固定显示演示日期 `2025-12-31`，所有运营表都带 `demo_data = 1`。这些数据只能用于验证产品流程，不能当作企业真实经营结果。

## 3. 工具与路由

当前开放四类工具：

| 工具 | 权限 | 用途 |
| --- | --- | --- |
| `query_order` | 只读 | 查询订单状态、商品和金额 |
| `query_inventory` | 只读 | 查询可用库存、预留量和补货点 |
| `query_return_policy` | 只读 | 按品类检索退货窗口与注意事项 |
| `create_return_request` | 写入 | 创建演示退货申请 |

第一版使用确定性路由，不额外引入 LangGraph 或让大模型自由选择任意函数。原因是场景和工具数量很小，确定性路由更容易测试、解释和控制。后续只有在开放式表达导致路由 Bad Case 明显增加时，才考虑增加模型分类或图编排。

## 4. 退货申请工作流

```text
提取订单号和原因
-> 查询订单
-> 根据商品品类检索政策
-> 检查是否送达、是否在申请窗口内
-> 生成动作提议
-> 暂停并等待用户明确确认
-> 写入独立演示操作库
-> 返回申请编号和待人工复核状态
```

“满足申请条件”不等于“退款成功”。系统只允许创建待人工复核申请，不自动退款。

## 5. 安全设计

1. 分析数据库始终以 SQLite `mode=ro` 和 `PRAGMA query_only = ON` 查询。
2. 写操作不进入分析库，只写入 `agent_actions.db`。
3. `create_return_request` 必须收到显式 `approved=True`，否则抛出权限错误。
4. 每个退货提议根据订单号和原因生成幂等键，重复执行返回原申请。
5. 每次路由和工具调用记录会话、时间、工具、状态和说明。
6. 未知任务、缺少订单号或商品编号时不猜测，要求用户补充。

## 6. 评测

固定评测集位于 `eval/agent_tasks.csv`，共 30 条，覆盖：

- 存在和不存在的订单。
- 正常和未知商品库存。
- 多个品类的退货政策。
- 退货窗口内、超期和未送达订单。
- 缺少参数、未知对象和宽泛任务。
- 写操作是否停留在人工审批状态。

运行命令：

```powershell
python -m src.evaluate_agent
```

当前固定任务的路由和最终状态均为 30/30。该结果只说明这些预设任务回归通过，不代表开放式客服请求准确率。

## 7. 后续是否引入真正的模型规划

只有同时满足以下条件才继续增加模型路由或 LangGraph：

1. 收集到足够多无法由确定性规则处理的真实表达。
2. 一个任务确实需要动态选择步骤，而不是固定工作流。
3. 有可重复的评测集衡量增加模型后的收益和风险。
4. 能处理模型选错工具、参数错误、循环执行和成本上升。

在此之前，框架升级不是项目价值，稳定完成任务才是。
